title: "Environment variables"
description: "Set runtime and build-time variables for an app, and control who on your team can read their values."
---

Every app has its own environment variables. Symplax passes them to your container when it starts, and to your build when the build needs them.

## Add and edit variables

<Steps>
  <Step title="Open the Variables tab">
    Open your app and go to the **Variables** tab.
  </Step>
  <Step title="Add your variables">
    Click **New Variable**, type a name and a value, and choose **App only** or **App and build**. Press Enter or click **Add**. To add many at once, paste a whole `.env` file into the name field: every `KEY=VALUE` line becomes a variable, and comments and blank lines are skipped.
  </Step>
  <Step title="Save and redeploy">
    Your changes wait in a bar at the bottom of the list. Click **Save & Redeploy** to apply them, **Save** to keep them for the next deploy, or **Discard** to drop them. A saved variable is not live until the app redeploys.
  </Step>
</Steps>

To change a variable, click the pencil icon on its row. The eye icon shows a value and the copy icon copies it. **Search variables** and the filter (**All variables**, **App only**, **App and build**) narrow a long list.

You can also add variables in the last step of **Deploy App**, before the first deploy. Owners and admins can click **Export** to copy every variable or download them as a `.env` file.

<Tip>
  Setting `PORT` also tells Symplax which port to route traffic to. See [Port and health check](/apps/deploy-from-github#port-and-health-check).
</Tip>

## Runtime and build-time variables

Server code reads its configuration when it starts. Frontend frameworks are different: Next.js, Vite and the rest read some variables during `npm run build` and compile the values into the JavaScript they ship. A variable that only exists at runtime is missing from that bundle, and the build often fails while prerendering.

Symplax handles both:

<Tabs>
  <Tab title="Browser-exposed prefixes">
    Variables whose names start with one of these prefixes are passed to `docker build` as build arguments, and set as `ENV` after every `FROM` in your Dockerfile. They show a **Build** badge in the Variables tab.

    | Prefix | Framework |
    | --- | --- |
    | `NEXT_PUBLIC_` | Next.js |
    | `VITE_` | Vite |
    | `REACT_APP_` | Create React App |
    | `NUXT_PUBLIC_` | Nuxt 3 |
    | `PUBLIC_` | SvelteKit, Astro |
    | `GATSBY_` | Gatsby |
    | `EXPO_PUBLIC_` | Expo |
    | `VUE_APP_` | Vue CLI |

    These values end up in your image and in the JavaScript sent to every visitor. Never put a secret behind one of these prefixes.
  </Tab>
  <Tab title="Other variables you mark">
    A build sometimes needs a variable with any other name, such as `SENTRY_AUTH_TOKEN` or `API_BASE`. Each row in the Variables tab has an **App** or **Build** badge: click **App** to pass that variable to the build as a build argument too, and click **Build** to stop. When you add a variable, choosing **App and build** does the same.

    Like the prefixed ones, a marked variable is recorded in the image, so only mark values that are safe to keep there.
  </Tab>
  <Tab title="Everything else">
    All of your variables are also available while the build runs, as a BuildKit secret mount. Each shell-form `RUN` step in the Dockerfile can read them, so `next build` with Prisma, Payload or a CMS that needs `DATABASE_URL` or a secret key works.

    A secret mount is not stored in the image, its layers or its history. Exec-form steps (`RUN ["cmd", "arg"]`) and heredoc steps do not receive these values.
  </Tab>
</Tabs>

<Note>
  If your build connects to a Symplax database on the same server, the internal hostname does not resolve on the build machine. Symplax points the build at the database's public address only when you have already turned on [public access](/databases/public-access) for it. It never opens a database for a build.
</Note>

## Connect a database

Click **Connect Database** in the Variables tab to give the app a managed database's connection string, without copying it by hand.

<Steps>
  <Step title="Pick a database">
    The list shows your databases. One you cannot use from this app stays in the list, greyed out with the reason: it is stopped, or it is on another server with public access off.
  </Step>
  <Step title="Connect">
    Click **Connect and redeploy** to apply it straight away, or **Connect only** to apply it on the next deploy.
  </Step>
</Steps>

Symplax sets one variable for the engine: `DATABASE_URL` for PostgreSQL, `MYSQL_URL` for MySQL and MariaDB, `MONGODB_URL` for MongoDB, `REDIS_URL` for Redis and Valkey, and `CLICKHOUSE_URL` for ClickHouse. If the app already has that variable, it is replaced, and the dialog says so before you connect.

The address depends on where the app runs. An app on the same server as the database gets the internal address. An app on another server gets the public address, which only works while the database's [public access](/databases/public-access) is on. If that public access is set to expire, the dialog tells you when the app will lose the connection.

Removing a variable that a database, a secret or your mail settings provide asks you to confirm first. Mail variables are edited from your mail settings, not here. See [Databases](/databases/overview#connect-a-database-to-an-app).

## Encryption

Values are encrypted with AES-256-GCM before they are stored, and decrypted only when they are sent to a build or to your server, or shown to someone allowed to see them.

## Who can see values

On a team, what a person sees depends on their role. See [Team roles](/teams/roles).

| Role | What they see |
| --- | --- |
| Owner | Every value. |
| Admin | Every value. |
| Developer | Names, with every value masked. They can reveal one value at a time. |
| Viewer | Nothing. Viewers cannot open an app's variables. |

In a personal workspace, you are the owner.

A developer reveals a value by clicking the eye icon beside it. Every reveal is recorded in an audit log with who revealed it, the variable name and the app, never the value, before the value is returned. If the log entry cannot be written, the reveal is refused. Reveals are capped at 30 per person every 10 minutes.

Developers can still add and change variables. A masked value that they leave untouched is saved unchanged, so editing one variable does not overwrite the others.

<Note>
  API keys need the `secrets:read` scope to read variable values. See [API keys](/api/keys).
</Note>
